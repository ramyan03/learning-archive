Delegates / Events

    Delegates are type safe function pointers. Stores a method in variable and calls later -> 
    
        public delegate int MathOperation(int a, int b);
        
        int Add(int x, int y) => x + y;
        MathOperation op = Add;
        int result = op(2, 3); // 5

    Enables callbacks, strategy patterns, event systems, LINQ, async APIs 

    Built in
        Func<int, int, int> add = (a, b) => a + b; // Returns value and used to compute somthing
        Action<string> log = msg => Console.WriteLine(msg); // Returns void and used to do something
        Predicate<int> isEven = n => n % 2 == 0; // Returns boolean and used for testing

    Multicast Delegates
        Action notify = () => Console.WriteLine("Email sent");
        notify += () => Console.WriteLine("SMS sent");

        notify(); // Will output Email sent and SMS sent

    Can be invoked by outsiders and can be reassigned. 



    Events are delegates with rules -> Only owner can raise it and subscribers can add/remove, not invoke.

Eager v Lazy loading
    Eager loads related data immediately with the main Query. It uses .Include() method and executes a JSON query to get all data at once. Predictable, fewer queries, but might load unnecessary data. Still use as default choice.
    Lazy loading only loads related data when you access it. Requires virtual properties and proxy package. Executes seaparate queries when you access navigation properties. N+1 query problems, less predictable. Avoid in most cases.
    Explicit loading is manually load related data when needed. Use _context.Entry(entity).Collection().LoadAsync() -> Use only with UIs with unpredictable access patterns.

Migrations (track DB changes)
    Code files that represent changes to your database shema. They allow version control of your database structure. Key concepts are that each migration has an Up method (apply changes) and a Down method (revert changes). Migrations are sequential
    EF core tracks which migrations have been applied in a __EFMigrationsHistory table

Best practice
    Always pull latest code before creating migration to prevent conflicts when multiple devs working on same project. Use descriptive migration names such as AddUserEmailIndex.
    Review generated migration code.
    Do not modify existing migrations that have been pushed.
    Use seed data carefully.
    Handle production migrations carefully.

Repository pattern
    Design pattern that creates an abstraction layer between data access logic and business logic. Provides methods like GetByID, GetAll, Add, Update, etc.
    Hides EF core implementation details from business logic.
    Use it because of separation of concerns -> Business logic does not know about database details. Easy to mock repos in unit tests. Can swap out data sources without changing business logic. All queries are in one place.
    Can argue EF Cores DbSet<T> is already a repo but it depends on overall size and complexity of project.

N+1
    Most common EF core performance issue. Happens when query for N parent entities (1 query). Then loop through them and query for related data (N additional queries). Total is 1+N queries.
    To avoid this, use Include() to eager load related data in single query with JSONs. Select() to project only data you need. 

Pagination
    Never load all records from large tables
    Use Skip() and Take() to load pages
    Essential for tables with thousands of records

Filter before Include: 
    Apply Where() before Include() to reduce data loaded
    Only loads related data for filtered results

Indexes
    Ensure foreign keys and frequently queried columns have database Indexes
    Can configure in EF core using Fluent API

Architecture

    Separation of concerns
    Presentation Layer - Controller
        Handles HTTP requests
        Validates incoming data
        Returns appropriate status codes
        Must be thin and should delegate work to services. It should NOT contain business logic or directly access database.

    Business Layer - Services
        Contains your application's business rules
        Orchestrates operations between repositories
        Performs calculations, validations, and transformations
        Should focus purely on business operations and NOT know about HTTP or databases directly

    Data Layer = Repository
        Handles all database operations
        Executes queries and saves data
        Should be simple CRUD operations and should NOT contain busines logic

    Why? To be more maintainable, testabile (can test one layer without the others) and reusable. Also higher clarity.

Async
    Allows code to be non-blocking. Thread is released to handle other work when await is called
    Allows for scalability since application can handle more concurrent requests
    UI applications remain responsive during long operations
    Resource efficiency - better use of server resources
    How?
        When you await an I/O operation (query, request, read, etc.), the method pauses and returns control to caller. When operation completes, the method resumes
    When?
        Database operations, HTTP requests, File I/O (read, write)
    When NOT?
        CPU bound operations -> Use Task.Run() to run in background
        Simple operations
        Over-optimization
    Patterns 
        sequential async operations wait for one before starting next (use when operation B depends on result of operation A)
        parallel async operations start multiple at once and wait for all. Use Task.WhenAll() when operations are independent. Dramatically faster for multiple API calls/database queries
    Practices
        async all the way throughout the layer
        Dont use .Result or .Wait() to prevent deadlocks
        Always use async Task not async void
    
Authentication (who are you? -> Verifying, logging in) and Authorization (what can you do? -> Checking permissions, happens after Authentication)

    Authentication approaches
    Cookie based (traditional)
        Server creates session, sends cookie to browser. Browser sends cookie with each request. Good for server-rendered web apps.
    JWT (modern web apps)
        Server creates signed token containing user info. CLient stores token. Client sends token in Authorization header. Stateless. Good for APIs, microservices.
    OAuth 2.0 (third party)
        Login with Google, github, etc.
        Delegates auth to 3rd party 
        Good for avoiding password management, social Login 
    
    Authorization approaches
    Role base (RBAC)
        Users have roles such as Admin, User, Manager. Permissions granted to roles. Simple and common
    Claims based
        More flexible than roles. User has claims (key-value pairs such as Age, Department, etc.). Can check specific claims for Authorization
    Policy based
        Define complex authorization rules. Combine multiple requirements. Most flexible.
    
    Happens at controller level. At action level -> Different permissions for different endpoints. In business logic -> Check user permissions before performing operations.

SOLID
    Single responsiblity principle - Each class should only have one reason to change. Easier to understand and test. Changes in one area don't break the rest 
    Open/Closed principle - Open for extension, closed for modification. Add new functionality without changing code. Reduces risk of breaking existing functionality when adding features
    Liskov principle - Derived classes must be substitutable for their base classes. Given a base class, any derived class should be able to replace it without breaking program. Ensures inheritence is used correctly and polymorphism as well.
    Interface principle - Better to have small specific interfaces than one large, general interface. Classes only implement what they need, avoiding dummy implementation
    Dependency inversion principle - Depend on abstractions, not concretions. High level modules shouldn't depend on low-level modules. Both should depend on abstractions

                Round Robin -> Each server gets request in order and works best when servers are identical
                Least connections -> Send request to least busy server, works bset for long-lived requests
                Least response time -> First server to repond gets request, works best for latency-sensitive systems 
                IP hashing -> Same client goes to same server, used for session persistence
                Weighted variants -> Stronger servers get more traffic (most used in real world)
                Geographic routing -> Closest server wins
                Consistent hashing -> Minimizes reshuffling when nodes change. Critical for distributed systems
                Health checks, redundancy, DNS failover since if LB fails, everything fails
        Databases
            Relational -> Structured, ACID (Atomicity, Consistency, Isolation, Durability)
                Examples are MySQL, PostgreSQL
                Used for transactions, financial data, complex joins
            NoSQL -> Flexible, horizontally scalable (Split data across servers, range based, hash based, geo based, etc.), weaker consistency guarantees
                Examples are MongoDB, Redis
                Used for massive scale, fast iteration, unstructured data
            Vertical scaling
                Bigger machine
                Simpler but limited
                Single point of failure
            Horizontal scaling
                Sharding
                    Split across servers
                    Range based, hash based, geo based
                Replication
                    Duplicate data for availability 
                    Master slave -> Read scaling
                    Master master -> Write scaling, harder

Exceptions
- Errors are things like OutOfMemoryError. It is generally a more serious issue related to the system itself
- Exceptions are used to show what issues are occurring
- Exceptions can be separated into Checked (can catch with try, catch blocks) and Unchecked (Runtime error that should not be caught)
- Catch blocks work in reverse order where the most specific exception should come first and Exception e comes last

Good Design:

- Code Reuse (reused for different applications)
- Scalability (handle increase in traffic)
- Extensibility (easily extended)
- Maintainability (holds up to changing user needs)

SOLID → Single responsibility (class does one thing and one thing well)
		Instead of single User class handling both Login() and UpdateProfile(), split into AuthServices and UserProfileService
	Open/Closed (open on extension side (extends), closed for modification). Associated to abstraction and polymorphism
		Define Shape interface with CalculateArea() then any shapes can implement that to calculate area instead of using multiple if statements
	Liskov Substitution (subclasses should be usable everywhere their parent class is expected). Associated to Inheritance and polymorphism
		If Bird has fly(), Penguin should not inherit from it. Instead create Bird and then a subclass of FlyingBird
	Interface Segragation (Is a contract that can be implemented by classes. Prefer smaller, focused interfaces over large generic ones)
		Instead of having a general IMachine interface that can print(), scan(), fax(), create multiple Interfaces like IPrinter, IScanner, IFax
	Dependency Inversion (Abstractions not concrete implementations)
		Creating interfaces or abstractions to handle general methods widely used instead of concrete examples

Mockito
    Mock -> Fake object that does nothing by default. Use when you want to isolate class being tested from its dependencies
        Account mockAccount = mock(Account.class)
    Stubbing -> Telling a mock what to return when a method is called. Use when code depends on return value from a dependency
        when(mockAccount.getBalance()).thenReturn(500);
    Verify -> Checking that method was called ona a mock. Use when you want to confirm interactions happened
        verify(mockAccoount, times(2).withdraw(100))
    Spy -> Wraps real object. Real methods execute unless stubbed. Use when you mostly want real behaviour but need to verify calls
	
	Mock dependencies of the class not the class itself (When testing Company, mock Account, don't mock Company)
